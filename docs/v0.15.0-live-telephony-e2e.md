# v0.15.0 Live Telephony E2E Baseline

## 완료 정의

실제 시험 전화 한 통에서 아래 전체 경로를 통과해야 v0.15.0을 병합/태그한다.

1. 검증된 시험 휴대전화 → Twilio Trial Voice 번호/시험경로
2. Twilio `<Connect><Stream>` → 공개 WSS Media Gateway
3. Twilio `audio/x-mulaw`, 8 kHz mono → Gateway PCM16/16 kHz 변환
4. 8초 메모리 발화 버퍼 → WAV
5. 보호된 `/api/gateway-stt-ingest` → CLOVA STT
6. 보호된 `/api/gateway-stt-rag-answer` → 승인근거 검색/AI 답변
7. OpenAI `/v1/audio/speech` Server TTS
8. PCM → μ-law/8 kHz 변환
9. Twilio `media` + `mark` → 수화기에서 AI 음성 청취
10. 다음 발화 1회 또는 근거부족 fallback 확인

## 현재 자동 구현 완료

- `gateway/liveBridge.mjs`
- 전화 오디오 8초 메모리 버퍼링
- WAV 헤더 생성
- 한 실전화 통화에 하나의 STT session UUID를 사용하고 turn별 `chunkIndex`를 연속 증가
- 8초 경계에서 초과 수신된 작은 PCM remainder를 다음 turn 버퍼로 보존
- Gateway 전용 보호 API `/api/gateway-stt-ingest`, `/api/gateway-stt-rag-answer`, `/api/gateway-stt-session-complete` 추가
- Gateway → Vercel 요청에 `x-stt-internal-token` shared secret 인증 적용
- 비교 시 `timingSafeEqual` 사용, 토큰 미설정 시 503, 불일치 시 401 처리
- 기존 브라우저 PoC endpoint와 실전화 Gateway endpoint 분리
- 통화/소켓 종료 시 in-flight turn 종료를 기다린 뒤 보호된 session-complete를 best-effort 호출
- 승인근거 답변 → Server TTS → Twilio 송출
- OpenAI Server TTS를 24 kHz / 16-bit / mono PCM 계약으로 고정하고 TTS timeout 적용
- 근거 부족 → 담당자 확인 안내 후 live loop stop
- TTS 생성/재생 중 inbound audio 무시
- Twilio `mark` 수신 후 다음 청취 버퍼 초기화
- upstream STT/RAG HTTP timeout 적용
- Twilio start media format을 μ-law/8 kHz/mono로 검증
- Twilio WebSocket 서명을 공개 WSS URL 기준으로 검증하고 trailing-slash 변형도 허용
- `/v1/sessions`, `/v1/tts`, `/v1/clear` 제어면을 `GATEWAY_CONTROL_TOKEN`으로 보호
- 실제 통화 원시 오디오 파일/DB 저장 없음

## 데이터 보존 주의

보호된 `/api/gateway-stt-ingest`는 내부적으로 기존 STT ingest 로직을 사용하므로 **인식된 STT 텍스트를 `stt_poc` transcript 테이블에 저장**한다. v0.15는 실전화 한 통을 하나의 STT session으로 묶고, 인식된 turn은 연속 chunk로 저장하며 통화 종료 시 session 완료 처리를 시도한다. 따라서 v0.15 실전화 시험에는 실제 민원인 개인정보나 실제 사건 내용을 사용하지 않고, 아래에 정의한 비식별 합성 시험 문장만 사용한다.

- Gateway는 원시 통화 오디오 파일을 저장하지 않는다.
- Gateway 메모리의 발화 버퍼는 turn 처리 후 폐기한다.
- STT 인식문과 세션 상태는 기존 STT PoC 저장정책을 따른다.
- 실제 민원·개인정보를 연결하려면 별도 개인정보·보존기간·접근통제 검토가 필요하다.

## Gateway 필수 환경변수

```text
TELEPHONY_PROVIDER=twilio
LIVE_E2E_ENABLED=true
TWILIO_AUTH_TOKEN=<Twilio Console 값>
PUBLIC_MEDIA_WSS_URL=wss://<gateway-host>/v1/media
OPENAI_API_KEY=<existing OpenAI API key>
OPENAI_TTS_TIMEOUT_MS=30000
AI_APP_BASE_URL=https://comwel-ai-stt-poc.vercel.app
STT_INTERNAL_API_TOKEN=<Vercel과 Railway에 동일하게 설정할 강한 난수 secret>
GATEWAY_CONTROL_TOKEN=<Gateway 제어면용 별도 난수 secret>
LIVE_TURN_MS=8000
LIVE_HTTP_TIMEOUT_MS=20000
```

`STT_INTERNAL_API_TOKEN`과 `GATEWAY_CONTROL_TOKEN`은 서로 다른 값을 사용하고 GitHub/문서/로그에 실제 값을 기록하지 않는다. `AI_APP_BASE_URL`은 live mode에서 명시적으로 설정하며 localhost가 아닌 경우 HTTPS를 사용한다.

## Gateway → Vercel 보호 API

실전화 Gateway는 기존 브라우저용 endpoint를 직접 호출하지 않는다.

- `POST /api/gateway-stt-ingest`
- `POST /api/gateway-stt-rag-answer`
- `POST /api/gateway-stt-session-complete`

모든 요청에 다음 헤더가 필요하다.

```text
x-stt-internal-token: <STT_INTERNAL_API_TOKEN>
```

토큰 미설정 시 503, 잘못된 토큰은 401이다. shared secret은 Railway와 Vercel 환경변수에만 저장한다.

기존 브라우저 PoC가 사용하는 `/api/stt-ingest`와 `/api/stt-session-complete` 등은 v0.15 실전화 Gateway 경로에서는 사용하지 않는다. 이 분리는 기존 브라우저 기능을 깨뜨리지 않으면서 실전화 경로에 서버 간 인증을 추가하기 위한 것이다. 브라우저 PoC를 실제 운영으로 승격할 경우에는 별도의 사용자 인증·권한·요청량 제한을 추가 검토한다.

## 공개/보호 Gateway endpoint

공개 endpoint:

- `GET /health`
- `GET|POST /v1/twiml`
- `WSS /v1/media` — `X-Twilio-Signature` 검증 필수

보호 endpoint:

- `GET /v1/sessions`
- `POST /v1/tts`
- `POST /v1/clear`

보호 endpoint 호출 시 아래 중 하나를 사용한다.

```text
Authorization: Bearer <GATEWAY_CONTROL_TOKEN>
```

또는

```text
x-gateway-control-token: <GATEWAY_CONTROL_TOKEN>
```

## 별도 Gateway 배포 요구사항

- Node.js 20+
- 지속형 WebSocket 지원
- HTTPS/WSS 공개 URL
- TCP 443 외부 접근 가능
- 프로젝트 Root Directory: `gateway`
- Start command: `npm start`
- Health check: `GET /health`

Vercel Serverless Functions에는 장시간 Media WebSocket을 배포하지 않는다.

## 배포 후 사전점검

1. `GET /health`에서 `version=v0.15.0`을 확인한다.
2. `liveE2E.readiness.ready=true`인지 확인한다.
3. `liveE2E.internalApiTokenConfigured=true`인지 확인한다.
4. 토큰 없이 보호된 Vercel Gateway API가 401 또는 토큰 미설정 시 503인지 확인한다.
5. 올바른 `STT_INTERNAL_API_TOKEN`으로 보호된 Vercel Gateway API가 정상 처리되는지 확인한다.
6. 토큰 없이 `GET /v1/sessions`가 401 또는 설정 누락 시 503인지 확인한다.
7. 올바른 control token으로 `GET /v1/sessions`가 200인지 확인한다.
8. `GET /v1/twiml`이 동일한 WSS URL을 반환하는지 확인한다.

## Twilio Trial 설정

- Trial 가입 후 본인 휴대전화 번호 검증
- Voice Trial에서 할당된 시험 번호/허용된 번호 조합 확인
- Voice webhook/TwiML 요청 URL을 `https://<gateway-host>/v1/twiml`로 설정
- TwiML이 `<Connect><Stream url="wss://<gateway-host>/v1/media" />`를 반환하는지 확인
- trial 제한 때문에 검증된 전화번호만 사용

## E2E 시험 문장

실제 이름, 주민등록번호, 전화번호, 사건번호 등은 말하지 않는다.

첫 질문:

`개인정보가 포함된 실제 민원 원문을 입력해도 되나요?`

기대 결과:

- CLOVA STT 인식
- approved fixture 근거 검색
- AI 답변 생성
- 수화기에서 Server TTS 음성 청취

후속 질문:

`그럼 주민등록번호가 들어간 내용도 입력하면 안 되나요?`

기대 결과:

- 이전 대화 문맥 활용
- 승인근거 답변
- 수화기 자동 음성응답

새 주제:

`회사에서 이직사유를 권고사직으로 정정할 수 있나요?`

기대 결과:

- 승인근거 부족
- 담당자 확인 필요 음성 안내
- 자동 loop 중지

## 실전화 관찰값

보호된 `GET /v1/sessions`에서 다음만 운영검증에 사용한다.

- `sessionId`
- inbound/outbound frame 수
- turn 수
- `processing`, `speaking`, `stopped`
- STT chunk 수와 완료 상태
- `startedAt`, `lastSeenAt`

통화 종료 후에는 기존 STT 관리경로에서 해당 합성 시험 session이 `completed`로 전환되고 turn별 transcript chunk가 연속 인덱스로 저장되었는지 확인한다. `callId`와 provider call ID는 통신 문제 추적이 필요한 경우에만 확인하고 외부 문서나 화면 캡처에 남기지 않는다.

## 병합 금지 조건

아래 중 하나라도 미검증이면 v0.15.0을 main에 병합하지 않는다.

- 공개 WSS Gateway 미배포
- `/health` live readiness 미통과
- `STT_INTERNAL_API_TOKEN` 미설정 또는 Gateway↔Vercel 보호 API 인증 미통과
- Twilio 실제 Media Stream 미연결
- 실제 전화 inbound audio 미수신
- CLOVA STT 미통과
- 동일 STT session의 연속 chunk 및 종료 `completed` 상태 미확인
- RAG answer 미통과
- Server TTS 수화기 재생 미확인
- fallback 동작 미확인
- Gateway control endpoint 인증 미검증
- 합성 시험문장 외 실제 개인정보 사용
